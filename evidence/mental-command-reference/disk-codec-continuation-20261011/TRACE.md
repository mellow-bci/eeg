# Disk codec continuation: byte framing and independent-key comparison

Static arm64 LLDB against installed CortexService, SHA256 cdb5083641488056ceacfb8f2a0a0db724c8ce50585fd48aecbdcd1d179f936a. No vendor file/profile/key values consumed. One embedded salt literal was rendered automatically by LLDB and removed from the retained capture; original capture SHA256 is in manifest. No vendor literal/key is part of source or fixture.

## Compression body and inverse

FileCompress::eCompress 0x101e72560 calls qCompress(input,-1) at 0x101e72594, removes the first6 bytes at 0x101e725a4 and chops4 at 0x101e725b0. This removes Qt's size prefix and zlib wrapping, preserving raw DEFLATE. Header QDataStream writes five shorts: 0x1f8b,0x0800,0,0,0x000b (0x101e725d4..5f4), with no byte-order override. Qt documents default big-endian ([QDataStream](https://doc.qt.io/qt-6/qdatastream.html)); therefore resulting header is `1f 8b 08 00 00 00 00 00 00 0b`. A second stream sets byte order numeric1 at 0x101e72618, then writes checksum and original-size low32 bits at 0x101e72660/668: standard gzip CRC32 and ISIZE little-endian. The table-driven recurrence starts0xffffffff, consumes each source byte, shifts by8 and XORs a CRC table entry, then complements; empty input checksum0 (0x101e7261c..658). First CRC table entries read at 0x102fc9b04 match standard CRC32; table bytes are not copied into implementation. Header/raw-deflate/trailer concatenation occurs at 0x101e72694/6ec.

FileCompress::eUncompress 0x101e72870 rejects <=4 bytes through helper 0x10249ecec. It uses inflateInit2(windowBits47), zlib version1.2.11, structsize112 (0x101e728dc..8f0); then inflates into1024-byte chunks with Z_NO_FLUSH (0x101e72900..910). It returns empty on initialization failures and several inflate errors (0x101e7298c..998). The original stops when output buffer is not completely consumed rather than universally requiring Z_STREAM_END; its exact malformed/truncated output acceptance is not replicated. Native zlib47 supports gzip/zlib input. The independent codec deliberately requires completed single stream, no trailing bytes and an explicit output cap. This stricter failure policy is ours.

Implementation ReferenceDiskCodec uses native zlib raw-deflate with default compression/strategy to recreate framing. Byte output can differ across zlib releases for other inputs; equality on our analytic fixtures does not establish byte-identical Cortex compression on all data. It does not implement canonical Qt JSON serialization: callers supply bytes. Empty input emits valid gzip in our implementation; Qt qCompress empty special-case was not traced, so empty-input vendor byte equality is not claimed.

## Encryption and asset gate

LocalFileStore::encrypt/decrypt 0x101e7fbe0/0x101e7fb44 call helper0x101e80108 to produce a key, then AesCrypto with cipher numeric1. The key helper constructs an embedded37-byte salt, creates Qt hash algorithm numeric4 (0x101e8014c), adds salt local8Bit then caller identifier local8Bit separately, and returns the result (0x101e80150..208). **The embedded literal is vendor-dependent; it is redacted and deliberately unavailable to our implementation.** Exact identifier encoding and Qt enum interpretation are not implemented. No actual vendor file decryption is claimed.

AesCrypto::encrypt 0x101fdb4f8 cipher1 branch:
- RAND_bytes obtains16-byte IV and must return1 (0x101fdb5e0..5f0).
- EVP_aes_256_cbc at 0x101fdb630; helper0x101fdb7c4 receives callerkey/IV/input and encryptmode1; ciphertext begins output+16 (0x101fdb638..654).
- IV copied into first16 outputbytes, output trimmed to16+ciphertextlength (0x101fdb688..69c).
- helper calls EVP_CipherInit_ex/Update/Final; no padding disable appears (0x101fdb828/848/868). Native EVP default padding is the target. A follow-up own-fixture test found CommonCrypto PKCS7 native error semantics do not reliably reject invalid padding (see padding-validation.txt); ReferenceDiskCodec now decrypts raw CBC without native trimming, validates a finalcount1..16 and all finalbytes equal thatcount, then strips; invalid padding throws. This recreates strict EVP finalization error semantics and was checked again in the standalone authored-fixture script. No cipher/key/fixture was changed to fit the test. No authentication/tag is present in this body; CBC must not be advertised as authenticated storage.

AesCrypto::decrypt 0x101fdbb00 cipher1 branch takes first16 bytes as IV and remaining bytes as CBC ciphertext (0x101fdbce4..d40), then trims decoded output. ReferenceDiskCodec requires32-byte caller-owned key and16-byte explicitIV; encryption API is deterministic for comparison and caller must supply freshly randomized IV in any real application. It has no vendor salt/identifier key derivation or hidden key default. Actual application encryption remains independent, not a vendor compatibility claim.

## File path and durability semantics

LocalFileStore::saveFile 0x101e7fc7c composes directory/profileID/suffix string, constructs a FileLocker sidecar, checks isLocked (0x101e7fdb8..df0), then opens QFile with mode0x0a (write/truncate), writes data and closes (0x101e7fe08..e24). It checks only whether write result is negative, **not equality with requested byte count** (0x101e7fe1c). There is no QSaveFile, rename, flush or fsync call in this captured function. Closing does not prove durable media persistence. No atomic-save or full-write guarantee is inferred. Locker acquisition internals and filesystem behavior remain untraced; no claim of adequate interprocess safety follows from the method name.

LocalFileStore::readFile 0x101e7f5a0 checks QFile::exists, chooses direct read or FileLocker route according to memberflag; readData 0x101e7f990 opens/reads/closes. getThenDecrypt 0x101e7f450 first reads, propagates nonzero read error, then decrypts. TrainingAttributesStore::get(profileID,suffix,json) 0x101e73ac8 first readFile (0x101e73af4), maps file codes, decrypts (0x101e73b38), decompresses (0x101e73b4c) and QJsonDocument::fromJson (0x101e73b6c). Failed decryption returns0x3304 (0x101e73d18); empty decompressed data or parseerror returns0x3302 (0x101e73da0/c60). Successful JSON parsing converts document.object and returns0 (0x101e73db0..dcc); full object-root validation is not asserted. This completes the body-supported inverse byte path but does not implement typed profile import.

The earlier persistence-cache continuation proves manager save queues the worker and immediately returns0; that enqueue result is separate from worker completion and both are separate from fsync/durability. ReferenceDiskCodec contains no file writer and therefore promises none of these.

## Supported API and tests

Internal ReferenceDiskCodec(maximumPlaintextBytes:maximumEncodedBytes:) provides compress(Data), decompress(Data), encrypt(Data,key:Data,iv:Data), decrypt(Data,key:Data). All methods throw on invalid input or caps; no mocksuccess. Plaintext max applies compression/decompression; encoded max bounds envelopes/compressed bytes. These limits are explicit caller configuration, not recovered vendor limits. Compression encrypted composition uses compress→encrypt and decrypt→decompress. Allocation bounded by configured limits; unsupported gigantic sizes are rejected before UInt32 conversion.

Five tests use only authored phrase 'EEG independent fixture', keybytes0..31 and IVbytes0..15. Independent known answers were generated by command-line OpenSSL AES256CBC and Python zlib; test fixtures include gzip bytes, cipher bytes and an invalid-padding zero-block cipher. Tests cover roundtrip, exact known-answer encoding, gzipCRC corruption, truncation/trailingdata, plaintext/encoded caps, key/IV/frame mismatch and invalidpadding (zero count, count17 and inconsistent01,02). No trained asset is required. Parent coordinates package test execution; this agent did not build or commit.

Remaining: permitted own-key comparison against actual Cortex outputs (not performed), vendor salt/key compatibility authorization and text encoding, Qt JSON/matrix typed import/export semantics, locker/file rollback and durable/atomic persistence redesign. Reproducing unsafe partial-write/truncated-stream acceptance is not a product goal. No end-to-end vendor profile or mental-command parity claim follows from this codec checkpoint.
